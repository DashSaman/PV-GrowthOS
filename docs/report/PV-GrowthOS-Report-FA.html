۱خلاصه مدیریتی

PV GrowthOS یک سیستم خودکارسازی رشد است که روی همان سرور پرووداکشن زنده‌ی VPN شبکه PV مستقر می‌شود — سروری که همین حالا مشتریان واقعی روی آن سرویس دارند و سرویس‌های فروش (میرزا)، پنل نمایندگی، ربات AKH و زیرساخت تونل‌ها روی آن فعال‌اند. فلسفه طراحی این پروژه یک جمله است: رشد فروش با کمترین دخالت دستی، بدون به خطر انداختن حتی یک سرویس موجود.

فیچر فلگ مستقل

سه تصمیم بنیادین، کل پروژه را تعریف می‌کنند:

  • مونولیت ماژولار به جای میکروسرویس: سرور فقط ۲ هسته CPU و حدود ۴ گیگابایت رم دارد؛ پخش کردن سرویس‌ها هدر دادن منابع است. همه ماژول‌ها داخل یک ران‌تایم (pv-growth-app) زندگی می‌کنند ولی مرزهای داخلی‌شان آن‌قدر تمیز نگه داشته می‌شود که در آینده بتوان ورکرها را بدون بازطراحی جدا کرد.
  • بدون پلتفرم سنگین: PostHog، Mautic، GrowthBook، n8n و استک Grafana صرفاً مرجع مفهومی‌اند. فقط زیرمجموعه کوچکی از مفاهیم آن‌ها (رویداد، قیف، سگمنت، آزمایش) به‌صورت سبک و روی PostgreSQL پیاده می‌شود.
  • ایمنی مطلق نسبت به پرووداکشن: میرزا منبع حقیقت فروش باقی می‌ماند؛ گروث‌او‌اس فقط از بیرون و به‌صورت فقط‌خواندنی یا افزایشی به آن وصل می‌شود. با خاموش بودن همه قابلیت‌های گروث‌او‌اس، رفتار میرزا باید بیت‌به‌بیت مثل قبل بماند.

۲هدف تجاری و قیف رشد

هر قابلیتی که در این پروژه پیاده شود باید به‌وضوح حداقل یکی از این‌ها را تقویت کند: جذب کاربر واجد شرایط، افزایش تبدیل تست‌به‌پرداخت، افزایش تمدید، بازگرداندن کاربر ازدست‌رفته، افزایش معرفی، رشد کانال نمایندگی/افیلیت، بهبود اتریبیوشن یا بهبود خودکارسازی عملیاتی. قابلیت‌هایی که صرفاً «جالب» هستند پیاده نمی‌شوند.

۶سیستم کار و مدل رویداد

صف کار پایدار — بدون Redis

در نسخه اول، Redis لازم نیست؛ کارها روی PostgreSQL ذخیره و اجرا می‌شوند. هر کار این ویژگی‌ها را دارد: زمان‌بندی، تعداد تلاش مجدد با استراتژی backoff، کلید یکتایی/idempotency، وضعیت، locked_at/locked_by، started_at/finished_at، جزئیات خطا و retry_after.

تضمین کلیدی
اجرای هم‌زمان یا تکراریِ چند نمونه زمان‌بند هرگز نبتواند یک پست کمپین یا پیام مشتری را دوباره ارسال کند. این تضمین با کلید یکتایی + قفل ردیفی در سطح دیتابیس اعمال می‌شود و در تست‌ها به‌صورت اختصاصی پوشش داده می‌شود.

۷اتصال به میرزا و موتور اتریبیوشن

آداپتر میرزا — منبع حقیقت

میرزا برای کاربران (در حد نیاز)، سفارش‌ها، پرداخت‌ها، پروویژن، ساخت سرویس VPN و تمدید، منبع حقیقت باقی می‌ماند. GrowthOS هیچ منطق پرداخت یا پروویژنی را duplicate نمی‌کند. ترتیب ترجیحی یکپارچه‌سازی:

۱. API/رابط موجود میرزا  ←  ۲. آداپتر غیرتهاجمی  ←  ۳. یکپارچگی فقط‌خواندنی دیتابیس (در صورت امن بودن)  ←  ۴. هوک/رویداد افزایشیِ حداقلی — فقط در صورت ضرورت
معیار پذیرش فاز ۱
با غیرفعال بودن تمام قابلیت‌های GrowthOS، رفتار میرزا باید دقیقاً مثل قبل بماند — هیچ رگرسیون پرداخت یا پروویژنی قابل قبول نیست.

موتور اتریبیوشن

اتریبیوشن first-touch و last-touch هر دو ذخیره می‌شوند و first-touch هرگز بازنویسی نمی‌شود. منبع از پارامتر دیپ‌لینک start=<source> استخراج می‌شود:

الگومعنا
freecfg_<campaign>پست کانفیگ رایگان یک کمپین
ref_<user>لینک معرفی یک کاربر
partner_<partner>لینک همکار/افیلیت
seo_<page>ورود از صفحه سئو
channel_<campaign> · social_<campaign>کمپین کانال یا شبکه اجتماعی

برای هر منبع ردیابی می‌شود: source، campaign، medium، referrer، first/last_seen، bot_start، trial، purchase، revenue و درآمد تمدید — تا پاسخ سوال کلیدی «کدام منبع، مشتریِ باارزش می‌سازد؟» داده‌محور باشد.

۸موتور جذب کانفیگ رایگان

کانال کانفیگ رایگان، موتور اصلی جذب سرنخ واجد شرایط است و از دو استخر کاملاً مستقل تغذیه می‌شود:

شکل ۳ — خط تولید دوگانه کانفیگ رایگان: استخر عمومی (سبز) و استخر اختصاصی PV (آبی)

استخر عمومی (Public Pool)

کانفیگ‌های عمومی از رجیستریِ اداره‌شده توسط ادمین (منابع تأییدشده گیت‌هاب/تلگرام) جمع می‌شوند و از این خط تولید عبور می‌کنند:

Fetcher → Parser → Normalize → Deduplicate → Validate → Quality Score → Limited Health Check → Rank → Publish
  • فیلتر مرحله‌ای: نمونه واقعی — دریافت ۲۰۰۰ ← حذف تکراری ← ۵۰ نامزد ← بررسی اتصالِ محدودِ همان برترین‌ها ← انتشار فقط ۱ تا ۲ مورد. هیچ تستِ خشنِ هزاران اتصالی از روی این سرور VPN اجرا نمی‌شود.
  • اعتبار منبع: معیارهای قابلیت اعتماد هر منبع ذخیره می‌شود تا کیفیت رجیستری به‌مرور خودتصحیح شود.
  • صداقت برند: کانفیگ‌های عمومی صراحتاً «منبع عمومی/کامانیوتی» برچسب می‌خورند — هرگز القا نمی‌شود که PV Network آن‌ها را اداره می‌کند.

استخر اختصاصی PV (PV Exclusive Pool)

کانفیگ‌های رایگانِ محدود با استفاده از پروویژن مجاز PV Network ساخته می‌شوند. ادمین بدون هیچ تغییر کد می‌تواند این‌ها را تنظیم کند:

پست در روزساعات انتشارحجم ترافیک (GB)اعتبارلوکیشنپروتکل/پروفایلسقف claimمحدودیت هر کاربربازه تاریخ کمپینلوکیشن جایگزین

اورراید تاریخ: مثلاً ۳ اکتبر ← ۵ گیگابایت، ۴ اکتبر ← ۱۰ گیگابایت، ۵ اکتبر ← ۳ گیگابایت — صرفاً با تنظیم، بدون تغییر کد. جریان ترجیحی تبدیل:

پست کانال ← دیپ‌لینک ردیابی‌شده ← شناسایی کمپین توسط ربات ← بررسی واجد شرایط بودن ← سرویس موقت یکتا ← اعمال سهمیه/انقضا ← ثبت رویداد ← پیگیری خودکار

حالت «اشتراک عمومیِ کنترل‌شده» هم پشتیبانی می‌شود، اما مدل ترجیحیِ تبدیل، claim انفرادی است — چون اتصال کاربر به کمپین، سقف مصرف و هویت او قابل ردیابی و پیگیری است.

ترکیب محتوای کانال رایگان

کانال رایگان نباید به بڑِ کانفیگ بی‌کیفیت تبدیل شود. ترکیب محتواییِ قابل تنظیم: کانفیگ عمومی، کانفیگ اختصاصی PV، نکته رفع اشکال، ابزار مفید شبکه/VPN، دعوت به خرید و کمپین معرفی — همه زمان‌بند‌محور. ممنوع: کمیابی ساختگی، آپ‌تایم جعلی و تعداد کاربر غیرواقعی.

۹موتور پیام و محتوای کانال

قاعده طلایی پیام: داده ساختاریافته، نه تخیّل

هوش مصنوعی فقط لحن را بازنویسی می‌کند — هرگز اعداد تجاری را نمی‌سازد
قیمت، تخفیف، پهنای باند، سهمیه ترافیک، دسترسی سرور، آپ‌تایم، تعداد مشتریان و سقف claim باید از داده ساختاریافته بیایند. جعل هرکدام از این اعداد در پیام، نقض مشخصات است.

قالب‌های پیام با متغیر پارامتری می‌شوند:

{{location}}{{traffic_gb}}{{validity_hours}}{{price}}{{campaign_name}}{{bot_link}}{{expires_at}}

قالب‌ها بر اساس نیت جدا می‌شوند: جذب، آموزش، پیگیری تست، بازیابی خرید، تمدید، انقضا، وین‌بک، معرفی، همکاری و پشتیبانی.

موتور محتوا (Content Engine)

موتور محتوا برای کانال رسمی PV و کانال کانفیگ رایگان، محتوای زمان‌بندی‌شده (آموزشی، وضعیت سرویس، کمپین خرید، کمپین معرفی) تولید و منتشر می‌کند. چرخه عمر هر رکورد محتوا:

draft → validated → scheduled → published → failed   ·   حقایق تجاری ساختاریافته قبل از انتشار اعتبارسنجی می‌شوند

توقف هوشمند
وقتی خرید انجام می‌شود، همه یادآورهای فروشِ نامناسب بلافاصله متوقف می‌شوند — مشتریِ پول‌داده هرگز پیام «هنوز خرید نکردی» نمی‌گیرد. این رفتار در فاز ۳ با تست اختصاصی پذیرش می‌شود.

۱۱موتور معرفی، گیمیفیکیشن و همکاری

موتور معرفی (Referral)

کدهای معرفی یکتا، اتریبیوشن معرف، وضعیت pending، اعتبارسنجی، پاداش، تاریخچه پاداش و محافظت ضدتقلب. قاعده نام شکست‌ناپذیر: هرگز فقط برای کلیک روی لینک پاداش داده نمی‌شود. مسیر ترجیحی اعتبارسنجی:

کاربر معرفی‌شده ← شروع ربات ← (تست اختیاری) ← خرید واجد شرایط ← تسویه پرداخت ← اعتبار referral ← پاداش

محافظت‌ها: خود‌معرفی، حساب‌های تکراریِ قابل‌شناسایی، فارمینگ سریع و پردازش تکراری پاداش. مبلغ و نوع پاداش کاملاً قابل تنظیم است.

گیمیفیکیشن

ماسک‌های اختیاری (مثلاً ۱ معرفی معتبر ← پاداش A، ۳ ← پاداش B، ۵ ← پاداش C، ۱۰ ← پاداش D) به‌همراه کمپین‌های جدول امتیازات (leaderboard). همه مقادیر تجاری قابل تنظیم — هیچ عدد تجاری در کد هاردکد نمی‌شود.

افیلیت / همکار / نماینده

چهار لایه متمایز: معرفی مشتری، افیلیت، همکاری و نمایندگی. برای هر همکار ذخیره می‌شود: کلیک، شروع‌ها، تست‌ها، سفارش‌ها، فروش، درآمد، کمیسیون، کمیسیون در انتظار و کمیسیون تأییدشده. پنل نمایندگی موجود بازسازی نمی‌شود — یکپارچگی آن به فازهای بعدی موکول می‌شود و ربات‌های وایت‌لیبل صرفاً بک‌لاگ‌اند.

۱۲امتیازدهی سرنخ و سگمنت‌ها

امتیاز سرنخ (Lead Scoring)

امتیازدهی کاملاً قابل تنظیم بر اساس سیگنال‌هایی مثل: شروع ربات، دریافت کانفیگ رایگان، اتصال تست، مشاهده تعرفه، شروع تسویه، خرید قبلی، معرفی و انقضای اخیر. استراتژی نهایی امتیازدهی و آستانه‌های سگمنت هرگز در منطق تجاری هاردکد نمی‌شوند — از پیکربندی می‌آیند.

رصد هدفمند رقبا

فقط هوشمندی هدفمند — نه خزنده اینترنتیِ بی‌کنترل. منابع عمومیِ رقبا که ادمین تنظیم کرده برای تغییرات قیمت، پیشنهاد تست، حجم ترافیک، لوکیشن‌ها، کمپین معرفی، پلن جدید و پروموشن‌های بزرگ رصد می‌شوند. برای هر تغییر ذخیره می‌شود: منبع، زمان مشاهده، فیلد تغییرکرده، مقدار قبلی، مقدار جدید و URL منبع. قیدهای ایمنی: هرگز با ترافیک VPN تداخل نمی‌کند، در نسخه اول بدون اتوماسیون مرورگر و با HTTP fetching سبک.

۱۴تحلیل، آزمایش A/B و پنل ادمین

تحلیل (Analytics)

داشبورد ادمین باید این پرسش‌ها را پاسخ دهد: کاربران از کجا آمده‌اند؟ کدام پست کانفیگ رایگان به خرید می‌رسد؟ کدام کمپین تبدیل می‌شود؟ کدام منبع تمدید می‌سازد؟ کدام منبع معرفی درآمد می‌سازد؟ کدام پیام چرخه حیات به خرید ختم می‌شود؟ متریک‌های حداقلی: کاربران، شروع ربات، تست‌ها، claimهای رایگان، شروع تسویه، خریدها، نرخ تبدیل، درآمد، تمدیدها، نرخ تمدید، معرفی‌ها، درآمد معرفی، درآمد وین‌بک و LTV (در صورت کفایت داده) — همه با کوئری قیف و کوهورتِ سبک روی PostgreSQL، بدون نصب پلتفرم سنگین.

موتور آزمایش (Experiments)

  • تخصیص A/B قطعی (deterministic) — تخصیص یک کاربر در طول آزمایشِ در حال اجرا هرگز تغییر نمی‌کند و در دیتابیس ماندگار است
  • دامنه آزمایش: متن پیام، CTA، سهمیه تست، زمان انتشار، پیشنهاد کمپین، زمان‌بندی پیگیری
  • بدون نمونه کافی، برنده اعلام نمی‌شود — فقط گزارش نتایج

پنل ادمین

حداقلی اما کارکردی — اولویت با عملکرد است نه طراحی. ادمین می‌تواند کمپین‌ها، برنامه کانفیگ رایگان، رجیستری منابع، قالب‌ها، قوانین اتوماسیون، قوانین معرفی، سوابق همکاران، فیچر فلگ‌ها و آزمایش‌ها را مدیریت کند. داشبورد: سلامت سیستم، کارهای شکست‌خورده، رویدادهای اخیر، قیف فروش و عملکرد کمپین.

۱۶سیاست بیلد، امنیت و مشاهده‌پذیری

سیاست بیلد — بیلد سنگین روی پرووداکشن ممنوع

ممیزی نشان داده یک بیلد داکر تقریباً یک هسته CPU کامل را مصرف می‌کند. مسیر استاندارد:

GitHub Actions ← بیلد ایمیج ← تست ایمیج ← انتشار به رجیستری ← pool/deploy روی سرور

CI شامل lint، تست واحد، تست یکپارچه، بررسی امنیتی و بیلد داکر است. اگر اعتبار رجیستری در دسترس نباشد، بلاکر ثبت و کار توسعه/تست ادامه می‌یابد — بیلد سنگینِ خاموش روی سرور تولیدی هرگز انجام نمی‌شود.

امنیت

  • هیچ توکن، رمز، کلید خصوصی، اعتبار دیتابیس، توکن ربات تلگرام یا اعتبار پرداختی در گیت ذخیره نمی‌شود — همه از محیط/secret می‌آیند
  • کاربر دیتابیس با حداقل دسترسی؛ سرویس‌های داخلی فقط روی localhost یا شبکه اختصاصی
  • ادمین بدون احراز هویت غیرممکن است؛ CSRF در جاهای لازم، rate limiting، اعتبارسنجی ورودی، دسترسی SQL امن و لاگ امنیتی ساختاریافته
  • اعتبار VPN مشتریان لاگ نمی‌شود مگر با ضرورت قطعی و محافظت‌شده

مشاهده‌پذیری

لاگ ساختاریافته سبک به‌همراه: endpoint سلامت (health)، آمادگی (readiness)، متریک کارها، عمق صف، کارهای شکست‌خورده و خطاهای پردازش رویداد — با نمای CLI/ادمین برای بررسی سلامت. هیچ سوئیت مشاهده‌پذیری سنگینی در نسخه اول نصب نمی‌شود.

۱۷پاکسازی SentinelX و دستورهای ممنوع

حذف کنترل‌شده‌ی sentinelx-worker (فاز ۰)

مالک اعلام کرده این کانتینر لازم نیست: بدون پورت منتشرشده، روی شبکه bridge پیش‌فرض، بدون وابستگی Compose و بدون رابطه کشف‌شده با پنل نمایندگی یا ربات AKH. روش حذف:

  1. ثبت خروجی docker inspect برای rollback
  2. فقط همین یک کانتینر stop و remove می‌شود — نه پوشه /opt/sentinelx-worker (تا پایان تأیید استقرار GrowthOS)
  3. هرگز docker system prune یا docker network prune یا docker volume prune اجرا نمی‌شود

دستورهای مطلقاً ممنوع

docker system prune · docker network prune · docker volume prune · docker rm $(docker ps ...) · docker stop $(docker ps ...) · iptables -F · nft flush ruleset · git reset --hard (ریپوی نامرتبط) · rm -rf (پوشه‌های زیرساختی)
همیشه فقط منابعی هدف گرفته می‌شوند که متعلق به GrowthOS هستند.

اگر بعد از یک عمل GrowthOS هر یک از چک‌های سرویس محافظت‌شده شکست خورد: rollback فوری GrowthOS. تلاش تصادفی برای «تعمیر» سرویس محافظت‌شده ممنوع است.

قرارداد استقرار

preflight ← پشتیبان‌گیری وضعیت ← pool ایمیج تست‌شده ← مایگریشن ← راه‌اندازی GrowthOS ← چک سلامت ← تست دودی سرویس‌های محافظت‌شده ← موفقیت، یا rollback خودکار GrowthOS

GrowthOS فقط مالک /opt/pv-growth، منابع داکر خودش، دیتابیس/کاربر خودش، شبکه اختصاصی، vhost آپاچیِ صریحاً مجازِ آینده و لاگ‌های خودش است — مالک هیچ منبع پرووداکشن موجودی نیست.
